Arquitectura real (Session4)

Esto no es “un chat con un modelo”: es un flujo orquestado. La UI te muestra run_id/trace_id, y el backend ejecuta un grafo LangGraph que mantiene estado y produce un execution_summary.

Flujo (nodos)

  • planner: genera plan + queries. En modo fast suele ser fallback determinista.
  • researcher: ejecuta web_search/web_fetch y produce snippets/sources (suele ser el cuello de botella).
  • synthesizer: redacta respuesta con citas (puede ser determinista si LLM synth está desactivado).
  • anti_hallucination_guard: valida claims vs evidencia.
  • reflector: decide si final/hitl.
  • final: empaqueta respuesta.

Variables que realmente controlan latencia

  • WEB_MAX_QUERIES + WEB_FETCHES_PER_QUERY (I/O web).
  • WEB_CACHE_TTL_SECONDS (evita refetch en la misma sesión).
  • GRAPH_MODE y toggles ENABLE_LLM_* (LLM calls extra = más latencia).

Intención & queries (sin depender de regex)

Lección dura de Session4: el researcher es un “ejecutor” (busca/fetch), no es quien entiende al usuario. Si le pasas preguntas largas tal cual (ej. “¿Quién fue Isaac Newton?”), muchos proveedores devuelven poco o se desvían. El grafo necesita un paso explícito de normalización para generar queries estilo keywords.

Regla práctica

  • Entrada usuario puede ser larga, ambigua y con contexto.
  • Queries para web deben ser cortas, con entidad + intención + 1–2 keywords.
  • Idioma la respuesta final sigue el idioma del usuario; las búsquedas pueden mezclar idiomas si mejora recall.

Plantilla de conversión (ejemplos)

Usuario Mala query (tal cual) Buenas queries (keywords)
“Investiga acerca de Isaac Newton” BAD “Investiga acerca de Isaac Newton wikipedia” GOOD “Isaac Newton biography contributions”
GOOD “Isaac Newton Principia Mathematica”
GOOD “Isaac Newton laws of motion”
“¿Qué es internet?” BAD “¿Qué es internet? biography contributions” GOOD “Internet definition TCP/IP”
GOOD “Internet ARPANET history”
GOOD “Internet protocol suite TCP/IP”
“Analiza el impacto del trabajo remoto…” BAD 1 query gigante con todo el texto GOOD “remote work productivity studies 2023”
GOOD “remote work retention talent evidence”
TIP limitar por año/sector si hay demasiado ruido

Cómo depurarlo con observabilidad

  • Mira el nodo planner: ¿qué queries generó realmente?
  • Mira researcher: ¿0 snippets? entonces no hay evidencia → el resto del pipeline queda ciego.
  • Ajuste rápido: reduce queries, pero mejora su calidad; evita “pregunta completa + wikipedia”.

Modelos (Ollama) y estrategia

En Session4 vimos que “multimodelo” solo tiene sentido si cada nodo consume/produce salidas bien definidas y si las llamadas LLM realmente agregan valor. Sin RAG y sin APIs, el cuello de botella suele ser web I/O, pero aún puedes practicar: usar un modelo “rápido” para planificación/normalización y uno “mejor” para síntesis final.

  • Tokens/latencia si sube demasiado, baja WEB_MAX_* o desactiva nodos LLM no esenciales.
  • Formato si hay errores Pydantic/JSON, el problema suele ser prompt + parser, no el grafo.
  • Idioma si el modelo responde en otro idioma, es falta de instrucción en el último nodo (synth/final).

.env (Session4)

Regla #1: sin espacios alrededor de =. En Windows eso te rompe dotenv.

Variables críticas (las que más te afectan)

Variable Qué controla Notas
TRACE_PROVIDER Observabilidad nativa none, langsmith, langfuse. Cambias esto y reinicias server.
GRAPH_MODE Modo “fast” vs “full” Fast: latencia baja; Full: más llamadas LLM y más control (pero más costo).
WEB_MAX_QUERIES Cuántas queries se generan/usan Más queries = más recall, pero más latencia y más ruido.
WEB_FETCHES_PER_QUERY Cuántos fetches por query Más fetches = más evidencia, pero crece linealmente el tiempo de I/O.
WEB_CACHE_TTL_SECONDS Cache de fetch/snippets Clave para repetir preguntas sin volver a pagar el costo web.

1. Abre Docker Desktop
2. Espera a ver abajo “Engine running”
3. Verifica con:

  docker version

Si eso falla, NO sigas.

## 1) Descarga Langfuse (2 opciones)

### Opción A (recomendada): usar el repo oficial

  cd C:\IA_Local\scripts\Agentic_AI\Session4
  git clone https://github.com/langfuse/langfuse.git

## 2) Crea el archivo .env (EN LA RAÍZ) con secretos seguros

En la misma carpeta donde está el docker-compose.yml, crea .env con este bloque PowerShell:

  $NEXTAUTH_SECRET = [guid]::NewGuid().ToString("N")
  $SALT           = [guid]::NewGuid().ToString("N")
  $ENCRYPTION_KEY = -join ((48..57 + 97..102) | Get-Random -Count 64 | % {[char]$_})  # 64 hex chars

  $POSTGRES_PASSWORD = [guid]::NewGuid().ToString("N")
  $REDIS_AUTH        = [guid]::NewGuid().ToString("N")
  $CLICKHOUSE_PASSWORD = [guid]::NewGuid().ToString("N")
  $MINIO_ROOT_PASSWORD = [guid]::NewGuid().ToString("N")

  @"
  NEXTAUTH_URL=http://localhost:3000
  NEXTAUTH_SECRET=$NEXTAUTH_SECRET

  SALT=$SALT
  ENCRYPTION_KEY=$ENCRYPTION_KEY

  POSTGRES_USER=postgres
  POSTGRES_PASSWORD=$POSTGRES_PASSWORD
  POSTGRES_DB=postgres

  REDIS_AUTH=$REDIS_AUTH

  CLICKHOUSE_USER=clickhouse
  CLICKHOUSE_PASSWORD=$CLICKHOUSE_PASSWORD

  MINIO_ROOT_USER=minio
  MINIO_ROOT_PASSWORD=$MINIO_ROOT_PASSWORD
  "@ | Set-Content -Encoding UTF8 .\.env

  Write-Host "OK: .env creado en $(Get-Location)\.env"

## 3) Arregla el problema típico: puertos ocupados (5432/6379)

Como ya tenías Postgres local usando 5432 (y a veces Redis 6379), lo correcto es cambiar el puerto HOST, no el interno.

En docker-compose.yml:

### 3.1) Postgres
Busca:

  ports:
    - 127.0.0.1:5432:5432

Cámbialo por:

  ports:
    - 127.0.0.1:55432:5432

(Opción más segura: elimina el ports: completo si no necesitas acceder desde tu PC.)

### 3.2) Redis
Busca:

  ports:
    - 127.0.0.1:6379:6379

Cámbialo por:

  ports:
    - 127.0.0.1:56379:6379

Importante: dentro de Docker sigue siendo postgres:5432 y redis:6379.

Cómo leer trazas (para optimizar sin adivinar)

Usa la traza como instrumento de diagnóstico. Tu objetivo es convertir observaciones (“se demora”, “no encuentra”) en hipótesis verificables.

1) Encuentra el cuello de botella

  • Revisa el timeline: ¿qué nodo consume más tiempo?
  • En Session4 suele ser researcher por web I/O.

2) Valida la calidad de queries

  • Si ves queries tipo pregunta (“¿Quién fue X?”), el extractor de tema falló.
  • Preferible: keywords + entidad principal (ej.: isaac newton biography).

3) Revisa inputs/outputs por nodo

  • planner → plan/queries
  • researcher → snippets/sources/provider_errors
  • synthesizer → final_answer + citas

4) Cambia 1 variable y compara

  • Ej.: reduce WEB_MAX_QUERIES o sube caching TTL, y compara latencia.
  • Ej.: activa/desactiva ENABLE_LLM_PLANNER y observa si mejora queries (pero aumenta latencia).

Playbook de optimización (lo que haces con la “radiografía”)

Cuando ya ves el grafo y el timeline, la pregunta correcta no es “¿qué está mal?”, sino “¿qué palanca muevo para cambiar el resultado?”. Este playbook es una lista de palancas concretas y el criterio de éxito.

A) Si la latencia es alta

  • Revisa el timeline. Si el tiempo está en researcher, el problema es I/O web.
  • Baja WEB_MAX_QUERIES y/o WEB_FETCHES_PER_QUERY.
  • Sube caching TTL (WEB_CACHE_TTL_SECONDS) para re‑preguntas de la misma sesión.
  • Usa GRAPH_MODE=fast mientras iteras.

B) Si la calidad de búsqueda es mala

  • Inspecciona queries. Si son preguntas largas, extrae tema + keywords.
  • Activa planner LLM (ENABLE_LLM_PLANNER=true) solo si vale la pena el costo.
  • Introduce reglas: “queries como keywords”, “site:wikipedia.org” cuando aplique.

C) Si el idioma sale incorrecto

  • Verifica input_language en el state y que solo la salida final se traduzca.
  • Si una UI envía idioma “stale”, prioriza detección por texto.

D) Si hay alucinación / claims sin evidencia

  • El guard debe marcar puntos no soportados. Si no hay snippets, el problema es upstream (researcher).
  • Reduce claims. Prefiere “insufficient evidence” antes que inventar.

E) Si aparece bloqueo (403/429/CAPTCHA)

  • Es normal en scraping. Reduce frecuencia, agrega delay, limita fetches.
  • Prefiere Wikipedia/direct sources cuando sea posible.

LangSmith vs Langfuse (cómo elegir según objetivo)

No compiten “quién es mejor”: sirven para decisiones distintas. En Session4 dejaste ambos listos con pipeline nativo (solo cambias .env).

Cuándo usar Langfuse

  • Cuando quieres una vista visual tipo grafo/diagrama que te muestre el flujo de un vistazo.
  • Cuando quieres dashboards de observabilidad y seguimiento operacional (latencia, volumen, etc.).

Cuándo usar LangSmith

  • Cuando quieres integración fuerte con el ecosistema LangChain/LangGraph y workflows de evaluación/datasets.
  • Cuando quieres inspección detallada de runs, entradas/salidas y debugging profundo de componentes.

Cómo comparar “de forma justa”

  • Misma pregunta, mismos límites web, mismo modelo. Cambias solo TRACE_PROVIDER.
  • Comparas: latencia por nodo, errores, y facilidad para explicar un fallo concreto.
Nota práctica
Tu “enamoramiento” del grafo de Langfuse es normal: reduce el costo cognitivo. Aun así, LangSmith suele ser potente para “debug fino” cuando ya estás iterando prompts/evals.

Experimentos guiados (para aprender rápido)

Objetivo: dejar de “sentir” que algo mejoró, y empezar a medirlo. Aquí hay mini-experimentos que se validan con una traza en LangSmith o Langfuse. Cambia 1 variable por vez.

Experimento A — Mejorar queries (sin tocar límites)

  1. Pregunta 1: Investiga acerca de Isaac Newton
  2. En la traza, mira planner.queries y researcher.sources/snippets.
  3. Pregunta 2: Isaac Newton biography contributions
  4. Compara: ¿subieron snippets? ¿bajó la latencia? ¿mejoró la respuesta final?

Experimento B — Bottleneck (límites web)

  1. Con la misma pregunta, baja WEB_MAX_QUERIES y repite.
  2. Compara en timeline: ¿el nodo researcher baja proporcionalmente?
  3. Evalúa calidad: ¿todavía hay evidencia suficiente?

Experimento C — Idioma de salida

  1. Pregunta en español: ¿Qué es internet?
  2. La respuesta final debe salir en español aunque las fuentes estén en inglés.
  3. Si no ocurre, revisa el prompt del nodo final/synth (en ejercicios 5/5.1 esto debe quedar “blindado”).
Cómo cerrar el loop
Una traza útil siempre responde: qué pasó (inputs/outputs), dónde se fue el tiempo (timeline) y qué cambió entre un run y otro (comparación).

Troubleshooting (lo que realmente pasa en Session4)

Esta tabla está pensada como “libreta de guerra”: síntoma → dónde mirar (traza/log) → acción concreta. Úsala antes de tocar código.

Síntoma Qué mirar Causa típica Acción
Pending en UI de tracing Root run: ¿tiene end_time? ¿tiene outputs?
App: ¿status final es SUCCESS? 		Provider mal configurado o pipeline manual sin cierre/flush (deuda técnica).
También puede ser que estés viendo otro proyecto/env. 		Confirmar TRACE_PROVIDER + keys + project y reiniciar server.
Preferir pipeline nativo por callbacks.
0 snippets / 0 sources Nodo researcher: queries_used, provider_errors, latencia. Queries malas (pregunta completa), bloqueos web, o límites demasiado bajos. Mejorar queries (keywords). Revisar 403/429/CAPTCHA. Ajustar límites web.
Respuesta en idioma equivocado Nodo synth/final: ¿qué idioma “ordenó” el prompt? ¿hay un input_language en state? No se forzó “output_language = input_language” (o se tradujo en el nodo equivocado). Traducir solo al final si hace falta. En prompts de 5/5.1 exigir idioma del usuario.
Fuentes irrelevantes (QIP, acrónimos, etc.) Sources reales y snippets del researcher (no el texto final). Query ambigua (“internet” puede matchear acrónimos) + poca restricción de intención. Añadir keywords: “Internet TCP/IP definition”. Filtrar por Wikipedia/enciclopedia o añadir contexto.
Latencia enorme Timeline: ¿researcher o LLM nodes?
¿cuántos fetches por query? 		Demasiados fetches/queries, o demasiados nodos LLM en modo “full”. Reducir WEB_MAX_*, aumentar caching, desactivar nodos LLM no esenciales.
“Se ve rápido” pero la respuesta es pobre ¿cuántos snippets? ¿de qué calidad? ¿cuántas fuentes distintas? El sistema respondió determinista con poca evidencia (por límites o por queries malas). Subir ligeramente fetches o mejorar queries. Si no hay evidencia, mejor “insufficient evidence”.

Reglas anti-pérdida de tiempo

  • Primero valida .env (provider/keys/espacios) y reinicia server.
  • Luego mira planner → queries (calidad).
  • Luego mira researcher → evidencia (snippets/sources).
  • Último ajusta modelos/prompts si ya hay evidencia suficiente.
