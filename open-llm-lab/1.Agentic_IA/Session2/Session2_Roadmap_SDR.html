Arquitectura del runtime de agentes

Esta sesión introduce la mentalidad de “Agente + Herramientas” funcionando en tu PC, encima de modelos locales servidos por Ollama.

Piezas principales
Agent / Runner / Router
  • Agent:
    • Tiene name, role (prompt de sistema), model_name y tools.
    • Conserva su memoria (historial de mensajes).
    • Usa un cliente LLM local (call_llm_local) para hablar con Ollama.
  • AgentRunner:
    • Implementa el bucle percepción → pensamiento → acción → reflexión.
    • Interpreta las tool-calls devueltas por el modelo.
    • Decide cuándo parar (respuesta final al usuario).
  • ToolRouter:
    • Registra cada Tool por nombre.
    • Cuando el modelo pide {"tool": "fetch_html", "args": {...}}, el router invoca la función Python correspondiente.
Flujo alto nivel de una petición
Ciclo de acción
  1. El usuario escribe un mensaje (en Swagger o en la UI de chat).
  2. AgentRunner.run(...) construye el contexto:
    • Prompt de sistema (SDR_ROLE).
    • Historial de la conversación.
    • Mensaje de usuario actual.
  3. El modelo responde con texto normal o con un JSON que indica una tool-call.
  4. El ToolRouter ejecuta la herramienta Python pedida.
  5. El resultado se añade al contexto y se vuelve a llamar al modelo si hace falta.
  6. Cuando el modelo deja de llamar herramientas, se devuelve la respuesta final.
Este mismo patrón servirá después para agentes de RAG, SQL, automatización, etc.

Prompt Engineering del agente SDR (SDR_ROLE)

El rol define cómo piensa el agente. En esta sesión se construyó un prompt estructurado que separa claramente el modo chat normal del modo SDR.

Esqueleto lógico del rol
Componentes del prompt
  • 1) Comportamiento general
    • Sólo actúa como SDR cuando el usuario lo pide explícitamente.
    • Para preguntas normales (ej. “¿Qué día es hoy?”) responde de forma simple y directa.
  • 2) Uso de herramientas
    • Reglas claras para cuándo usar get_current_datetime, fetch_html, etc.
    • Prohibido inventar fechas: debe llamar a get_current_datetime.
  • 3) Activación del modo SDR
    • Se activa sólo si el usuario pide analizar empresas, investigar URLs o redactar correos.
    • En ese modo sí puede usar todas las herramientas y redactar mensajes de prospección.
  • 4) Manejo de errores [WEB_ERROR]
    • Cuando fetch_html no puede leer la web (403/404, etc.), el rol le ordena:
    • mencionar brevemente el problema,
    • seguir con un correo genérico basado en la información disponible,
    • hacer preguntas para ajustar (otra URL, contacto específico, etc.).
  • 5) Estilo
    • Profesional, breve, orientado a acción en modo SDR.
    • Conversacional y directo en modo chat normal.
    • Nunca devolver JSON al usuario final: siempre lenguaje natural.
Ver mini-plantilla de rol reutilizable ▼

Esta es una mini-plantilla textual que puedes adaptar para futuros agentes: 

[Identidad / Rol]
Eres un <tipo de agente> especializado en <dominio>. Solo debes activar ese rol especializado
cuando el usuario lo pida explícitamente.

[Comportamiento general]
- Para preguntas normales, responde de forma corta, clara y directa.
- No asumas tareas avanzadas ni prospección si el usuario no las solicita.

[Uso de herramientas]
- Usa herramientas solo cuando aporten valor.
- Define reglas claras para herramientas críticas (fechas, SQL, RAG, etc.).
- Nunca inventes información que deba provenir de una herramienta (fechas, consultas, etc.).

[Modo especializado ON]
Actívalo cuando el usuario:
- mencione <acciones clave> (ej. "analiza esta empresa", "haz un correo de prospección").
En este modo:
- usa la lista completa de herramientas,
- sigue el estilo correspondiente (profesional, técnico, etc.).

[Manejo de errores]
- Si alguna herramienta devuelve un error o datos incompletos:
  * menciona brevemente el problema,
  * ofrece una alternativa o una versión genérica,
  * formula preguntas para recopilar más contexto.

[Estilo]
- Resume, prioriza y orienta a acción.
- No devuelvas JSON al usuario final; solo texto legible.

Herramientas usadas en esta sesión

El agente SDR trabaja con un conjunto concreto de herramientas implementadas en Python. Aquí se resumen a nivel conceptual, con ejemplos de uso desde el chat.

fetch_html(url)
Web → HTML / [WEB_ERROR]

Descarga el HTML de una página web usando la conexión de tu PC. Si la respuesta no es 200 (403, 404, etc.) devuelve un mensaje que empieza por [WEB_ERROR] para que el agente sepa que hubo problema.

Ejemplo de prompt:
«Analiza https://openai.com y dime cuál es su propuesta de valor.»
En webs protegidas (como OpenAI) verás el comportamiento de degradación: menciona el error y genera una propuesta de valor genérica.
summarize_text(text, max_chars)
Recorte de texto

Recorta textos muy largos para no saturar al modelo. No es un resumen inteligente; sólo una reducción de tamaño para que el LLM haga el resto del trabajo.

Uso típico:
Internamente, el agente puede llamar a esta tool después de fetch_html si la web devuelve demasiado texto.
extract_value_proposition(raw_html)
HTML → contexto limpio

Limpia un poco el HTML (espacios, saltos) y lo recorta, produciendo un texto más manejable que el LLM puede usar para inferir la propuesta de valor de la empresa.

Uso típico:
Secuencia lógica: fetch_html → extract_value_proposition → análisis SDR.
generate_email_draft(...)
Plantilla de correo

Construye un prompt de alto nivel para que el modelo redacte un correo de prospección, incluyendo contexto de la empresa, persona objetivo, tono e idioma.

Ejemplo de uso desde el chat:
«Con lo que ya sabes de https://ejemplo.com, redacta un correo de prospección para el CTO, en tono profesional y en español.»
get_current_datetime()
Fecha y hora reales

Devuelve la fecha y hora actuales en formato ISO 8601 y humano (UTC). El rol obliga a usarla cuando se preguntan cosas como «¿qué día es hoy?».

Ejemplos de prompts:
«¿Qué día es hoy?»
«Usa tu herramienta interna de fecha y hora y dime la fecha actual.»

API & UI del chat local

Además del runtime interno, la sesión 2 añade la capa de exposición: endpoints HTTP y una UI minimalista de chat.

Endpoints principales
FastAPI @ 8100
  • GET / – health sencillo.
  • POST /sdr/email – flujo “clásico” SDR (sin chat, petición única).
  • POST /sdr/chat – chat con memoria por session_id.
  • GET /sdr/chat-ui – devuelve la página HTML del chat.

Puedes seguir usando /docs para probar JSON a bajo nivel: http://localhost:8100/docs.

Cómo levantar el servidor
Comandos básicos

Desde la carpeta de la Sesión 2:

cd C:\IA_Local\scripts\Agentic_AI\Session2
call ..\.venv\Scripts\activate.bat
uvicorn main:app --host 0.0.0.0 --port 8100 --reload

Luego abre en el navegador:

  • http://localhost:8100/sdr/chat-ui → chat con el agente.
  • http://localhost:8100/docs → documentación Swagger.
UI de chat (sdr_chat.html)
Experiencia de usuario
  • Interfaz de burbujas (usuario a la derecha, agente a la izquierda).
  • El session_id se guarda en localStorage, lo que mantiene la memoria del agente mientras uses la misma pestaña/navegador.
  • Se usa fetch contra /sdr/chat con JSON: {"session_id": "...", "message": "..."}.
  • La barra inferior permite:
    • Enviar con clic en Enviar.
    • Enviar con Enter o nueva línea con Shift+Enter.
Desde esta pantalla puedes “ver” el runtime en acción: uso de get_current_datetime, manejo de [WEB_ERROR], cambios tras ajustar el rol, etc., sin tener que mirar logs.
