Sesión 3 · Versión 3.0
De un solo agente a un crew multi-modelo para análisis de acciones

En esta sesión se evoluciona desde un agente SDR único (Sales Development Representative) a una arquitectura multi-agente que combina varios LLM locales (Qwen, DeepSeek, Llama, Qwen2.5) para analizar acciones bursátiles. El objetivo no es aún hacer research financiero profesional, sino entender la arquitectura de crew y ver a los modelos colaborar en una tarea concreta.

2 · Arquitectura mental
De un agente SDR a un Crew financiero local
SDR + Crew stock picker

El backend conserva el Agente SDR de la Sesión 2 (que sabe analizar webs, redactar correos B2B y manejar tiempo real con get_current_datetime), pero ahora añade un Crew de análisis de acciones que se activa explícitamente con el comando /stocks.

Alto nivel del endpoint POST /sdr/chat: 

if message.startswith("/stocks"):
    usar Crew de acciones (Sesión 3)
else:
    usar Agente SDR normal (Sesión 2)

Dentro del Crew, la lógica sigue un patrón de pipeline secuencial muy usado en frameworks de agentes como CrewAI o LangGraph:

  • Researcher (Qwen3:8b) recopila contexto de cada ticker (sector, negocio, datos básicos) usando yfinance.
  • Analyst (DeepSeek-r1:8b) traduce ese contexto en puntos fuertes, riesgos y oportunidades.
  • Writer (Llama3.1 8B) redacta un informe legible para humanos (introducción, análisis por ticker).
  • Judge (Qwen2.5:7b) revisa coherencia y estilo, ajustando el informe final al perfil de riesgo y horizonte indicados.

Piensa en esto como un equipo de analistas colaborando sobre la misma tarea, cada uno especializado, pero todos corriendo en tu propia máquina con modelos locales.

2.1 · Roles del crew
Mapa de agentes y modelos
Stock Picker Crew
Agente Modelo (Ollama) Responsabilidad principal Tipo de salida
Researcher qwen3:8b Buscar y sintetizar información general de cada empresa (sector, negocio, posición de mercado) a partir de datos de yfinance u otras fuentes básicas. Resumen por ticker + puntos clave.
Analyst deepseek-r1:8b Evaluar fortalezas, riesgos y oportunidades a partir de los resúmenes del Researcher; estructurar el análisis por categorías (negocio, tecnología, entorno competitivo). Lista estructurada de pros, contras y riesgos.
Writer llama3.1:8b Convertir el análisis previo en un informe fluido, legible y coherente en español, adaptado al perfil de riesgo (moderado) y horizonte (mediano plazo). Informe en formato Markdown / texto corrido.
Judge qwen2.5:7b Revisar el informe final, detectar inconsistencias, equilibrar el tono, y asegurarse de que la conclusión sea razonable dado el perfil del lector (inversor particular). Informe ajustado + conclusión general.

En futuras sub-sesiones (3.1, 3.2, 3.3) estos mismos roles pueden enriquecerse con datos más profundos (APIs financieras, RAG, debates bull vs bear, etc.) sin cambiar la estructura básica del crew.

3 · Tools concretas de esta sesión
Herramientas disponibles para el Agente SDR y el Crew
Tool-calling local

Las herramientas son funciones de Python expuestas al agente de forma estructurada (como “tool-calls”), de modo que el modelo puede decidir cuándo usarlas. En esta sesión se combinan tools ya vistas en la Sesión 2 con nuevas tools orientadas a acciones.

3.1 · Tools del Agente SDR (heredadas de la Sesión 2)

  • fetch_html(url) — Descarga el HTML básico de una web para extraer contenido. Útil para analizar páginas de empresas (cuando no hay errores 403/404).
  • summarize_text(text) — Resume textos largos (por ejemplo, una landing page) en pocos párrafos relevantes.
  • extract_value_proposition(text) — Intenta extraer la propuesta de valor central de una empresa o producto a partir del texto de su web.
  • generate_email_draft(context) — Construye una estructura de prompt interno para redactar un correo de prospección B2B alineado a la web analizada, el rol objetivo y el tono deseado.
  • get_current_datetime() — Devuelve fecha y hora actuales (desde el servidor). El sistema prompt del SDR deja claro que para preguntas como “¿Qué día es hoy?” debe usarse siempre esta tool en lugar de inventar fechas.

3.2 · Tools para el Crew de acciones

  • yfinance_fetch(ticker) — En la práctica se implementa usando yfinance.Ticker(ticker).info, lo que permite obtener nombre de la empresa, sector, industria, capitalización y algunos ratios básicos. No es una API institucional, pero sirve como “combustible mínimo” para el Researcher.
  • compose_stock_report(research, analysis) — Función que combina resúmenes del Researcher y el Analyst para que el Writer genere un informe legible en Markdown.
  • judge_stock_report(report, profile) — Tool lógico que pasa el informe al Judge para validar tono, coherencia y adecuación al perfil de riesgo (cauteloso, moderado, dinámico).

Estas tools son deliberadamente sencillas. La prioridad es entender el patrón de “un LLM decide cuándo usar tools” más que la sofisticación financiera. La mejora de datos vendrá en 3.1+.

4 · Herramientas para agentes profesionales
Catálogo orientativo de tools que valen la pena aprender
Referencia para futuro

Más allá del ejercicio de esta sesión, un arquitecto de agentes profesional suele trabajar con un catálogo de herramientas amplio. Aquí se listan tipos de tools que se usan mucho en la práctica, para que tengas un mapa mental de hacia dónde puedes crecer.

4.1 · Web · búsqueda · RAG

  • Buscadores web / news: tools que llaman a APIs de búsqueda (por ejemplo, Bing, Brave, Google Custom Search) para encontrar páginas relevantes y luego pasan links a otras tools de scraping.
  • Scrapers de HTML: herramientas que limpian páginas, quitan menús y anuncios, y devuelven solo el contenido central de la web.
  • Embeddings + vectores: tools que generan embeddings (ej. nomic-embed-text o mxbai-embed-large) e indexan documentos en un vector-store (pgvector, Chroma, Qdrant, etc.) para hacer RAG (búsqueda semántica con contexto).

4.2 · Datos financieros y de mercado

  • Yahoo / yfinance — ideal para prototipos rápidos y datos básicos de acciones (precios históricos, info general), sabiendo que no es oficial. GitHub de yfinance.
  • Alpha Vantage — API gratuita con clave personal para precios históricos, FX y algunos indicadores técnicos. Documentación oficial.
  • Finnhub.io — API más completa (news, earnings, ratings de analistas, etc.), con plan gratuito limitado. Docs de Finnhub.
  • Financial Modeling Prep (FMP) — muy útil para estados financieros (Income Statement, Balance Sheet, Cash Flow) y ratios fundamentales. Docs de FMP.

4.3 · Bases de datos y SQL

  • Conectores a PostgreSQL, MySQL, SQLite o Snowflake permiten que un agente lance consultas SQL parametrizadas sobre datos empresariales internos.
  • Muchos frameworks de agentes (incluyendo CrewAI y LangGraph) usan un patrón donde un “SQL Agent” traduce preguntas de lenguaje natural a SQL y devuelve respuestas/tablas.

4.4 · Automatización y APIs

  • Tools para llamar APIs REST externas (por ejemplo, CRM, ERP, servicios de envío de emails, Slack, etc.).
  • Envío de correos, creación de tickets en herramientas como Jira, integración con calendarios (Google Calendar / Outlook), etc., todo orquestado por un agente.

4.5 · Documentos largos y PDFs

  • Tools para leer y trocear PDFs, presentaciones y documentos escaneados (a menudo combinando OCR), muy útiles para agentes legales, financieros o técnicos.
  • Combinados con embeddings y RAG, permiten que un agente responda preguntas sobre manuales, normas técnicas, reportes de earnings, etc.

No necesitas dominar todas estas categorías hoy. Esta lista sirve como brújula: cualquier stack de agentes serio terminará usando varias de estas familias de herramientas.

6 · Próximos pasos
Roadmap de esta familia de sesiones: 3.0 → 3.1 → 3.2 → 3.3
Visión de evolución

La Sesión 3.0 te deja con un prototipo funcional de Crew financiero local, pero todavía con datos básicos vía yfinance. Las siguientes sub-sesiones están pensadas para profundizar en datos y en patrones de colaboración entre agentes.

  • Sesión 3.1 · Crew + APIs financieras dedicadas
    Sustituir o complementar yfinance con APIs como Alpha Vantage, Finnhub o FMP para obtener: series históricas, estados financieros y ratios más confiables.
  • Sesión 3.2 · Análisis cuantitativo y scoring
    Añadir lógica para calcular tendencias de ingresos, márgenes, crecimiento y un pequeño sistema de scoring por ticker (por ejemplo, 0–100), usando a los agentes para interpretar esos números.
  • Sesión 3.3 · RAG financiero y/o debate bull vs bear
    Introducir un agente Bull y un agente Bear con acceso a corpus documental (earnings transcripts, reportes PDF, noticias) vía RAG, y un Judge que arbitra el debate para producir una recomendación resumida.

La ventaja de la arquitectura actual es que todo esto se puede añadir sin romper lo que ya funciona: el Agente SDR, el endpoint /sdr/chat y la UI seguirán siendo los mismos; sólo cambiarán las tools y la lógica interna del crew.
